# Parikshit – Security, Error Handling & Logging Strategies

**Version:** 2.0  

---

## 1. Security Posture

Parikshit deliberately downloads and analyses **untrusted** third-party repositories and executes code generated by LLMs. The security model therefore assumes:

- Repository content is hostile.
- LLM output is untrusted.
- The only trusted boundary is the host process + Docker sandbox.

### 1.1 Trust Boundaries

| Zone | Trust Level | Controls |
|------|-------------|----------|
| Browser | Untrusted | CSP, no secrets, XSS hygiene |
| API process | Trusted | Input validation, auth (if enabled) |
| Repo storage (read-only) | Untrusted data | Never executed, path sanitisation |
| Workspace checkouts | Untrusted | Only executed inside sandbox |
| Docker sandbox | Isolation boundary | `--network=none`, resource limits, non-root, read-only rootfs where possible |
| LLM provider | External | Only retrieved excerpts, redaction, tool allow-lists |

### 1.2 Sandbox Specification (Mandatory)

```bash
docker run --rm \
  --network=none \
  --memory=512m \
  --cpus=1.0 \
  --user 1000:1000 \
  --read-only \
  --tmpfs /tmp:size=64m \
  --tmpfs /workspace:size=256m \
  -v <workspace>:/workspace:ro \
  parikshit-sandbox:latest \
  <command>
```

- No outbound network under any circumstances.
- Resource limits always applied.
- Non-root user.
- Workspace mounted read-only unless the specific run needs write (then a fresh writable layer).
- Timeouts enforced both by Docker and by the runner process.
- All stdout/stderr/exit code captured; container destroyed after run.

### 1.3 Application-Level Controls

- **Ingestion safeguards:** size, file-count, path traversal checks, binary rejection, allowed Git hosts list.
- **Secret handling:** never log `.env` values; never send secrets to LLM; redact common secret patterns from retrieved chunks before prompt construction.
- **Prompt injection defence:** repository content is treated strictly as data; tool calls are allow-listed per agent role; no “execute arbitrary shell” tool exists outside the sandbox runner.
- **Citation integrity:** every citation is verified against the real file on disk before it is returned to the client. Unverifiable citations are stripped or the answer is regenerated once.
- **Approval gates:** no patch export, merge, or external side-effect without an explicit user approval record.
- **Auth (MVP):** `AUTH_DISABLED=true` is acceptable for single-user local/demo. When enabled, use short-lived JWTs or session tokens; never store long-lived secrets in the browser.

### 1.4 What Is Explicitly Not Protected in MVP

- Denial-of-service via extremely large legitimate public repositories (mitigated by hard size limits).
- Side-channel leakage via LLM provider (accepted risk; only public code is sent).
- Physical access to the demo machine.

### 1.5 What the Hash-Chained Ledger Does and Does Not Prove

**What it guarantees:**
- **Tamper-evidence against in-band modifications**: Any alteration, insertion, deletion, or reordering of historic entries breaks the SHA-256 hash chain and is immediately detected by `LedgerService.verify_chain()` and `scripts/verify_ledger.py`.
- **Database-level immutability**: SQLite triggers (`trg_ledger_entries_no_update`, `trg_ledger_entries_no_delete`) block `UPDATE` and `DELETE` queries at the database engine level.
- **Concurrent sequence safety**: Atomic `BEGIN IMMEDIATE` transactions and partial unique indexes `UNIQUE(project_id, sequence)` prevent sequence forks.
- **Deterministic verification**: Storing canonical JSON strings eliminates re-serialization drift.

**What it does NOT prove:**
- An adversary with full, raw filesystem write access to the SQLite file (`parikshit.db`) could rewrite history and recalculate the entire chain from the modified entry forward.
- **Recommendation for enterprise production**: Periodically anchor the latest head hash externally (e.g. publish to an RFC 3161 timestamping authority, signed Git commit tag, or append-only cloud storage).

## 2. Error Handling Strategy

### 2.1 API Error Envelope (Mandatory)

```json
{
  "ok": false,
  "error": {
    "code": "REPO_TOO_LARGE",
    "message": "Repository exceeds the 200 MB limit.",
    "details": { "size_mb": 312, "limit_mb": 200 },
    "correlation_id": "corr_01J..."
  }
}
```

- Every error response includes a stable machine-readable `code` and a `correlation_id`.
- HTTP status codes follow normal REST conventions (400 validation, 404 not found, 409 conflict, 429 rate limit, 500 internal).
- Internal exceptions are never leaked as stack traces to the client in production mode.

### 2.2 Long-Running Jobs

- All heavy operations (ingest, index, battle, heal) are asynchronous.
- Client receives a `job_id` immediately and either polls `GET /jobs/{id}` or subscribes to an SSE stream.
- Jobs have explicit timeout and cancellation support.
- Failed jobs store the error message and partial artifacts for debugging.

### 2.3 Agent & LLM Failures

- Limited retries with exponential backoff on transient provider errors.
- Hard budget circuit-breaker (session + daily).
- On structured-output failure, fall back to a safe “I could not produce a valid response” message rather than raw model text.
- Citation verification failure → regenerate once → if still invalid, return partially_grounded or unsupported status.

### 2.4 Sandbox Failures

- Captured as first-class `sandbox_runs` records (exit code, logs, duration).
- Timeout, OOM, and non-zero exit are distinct outcomes.
- Never treated as silent success.

## 3. Logging & Observability

### 3.1 Principles

- Structured JSON logs only.
- Every request and agent step carries a `correlation_id`.
- Logs must never contain secrets, full repository file contents, or raw LLM system prompts that include user secrets.
- Ledger is the primary durable audit trail; logs are operational.

### 3.2 Required Log Fields

```json
{
  "ts": "2026-10-10T16:30:00Z",
  "level": "info",
  "correlation_id": "corr_...",
  "project_id": "prj_...",
  "job_id": "job_...",
  "agent_role": "adversary",
  "event": "tool_call",
  "tool": "run_pytest",
  "duration_ms": 4200,
  "tokens_in": 1200,
  "tokens_out": 350,
  "msg": "pytest completed"
}
```

### 3.3 What to Log

| Event | Level | Notes |
|-------|-------|-------|
| API request start/end | info | method, path, status, latency |
| Job state transitions | info | |
| Agent step start/end | info | role, tokens, tools used |
| Citation verification failure | warn | |
| Sandbox start/finish | info | exit code, duration |
| Budget threshold crossed | warn | |
| Security-relevant events (approval, export) | info | always |
| Unexpected exceptions | error | with stack (server-side only) |

### 3.4 Metrics (Minimal for MVP)

- Request latency histogram
- Job queue depth
- LLM token consumption (per day / per project)
- Sandbox success / failure / timeout counts
- Citation verification pass rate

## 4. Security Verification Checklist (Must Pass Before Demo)

- [ ] Sandbox containers have `--network=none`
- [ ] Sandbox runs as non-root
- [ ] Resource limits (memory + CPU) are applied
- [ ] No secrets appear in logs or LLM prompts
- [ ] Citation verifier rejects non-existent paths / out-of-range lines
- [ ] User approval is required before any patch export
- [ ] Ledger entries form a valid hash chain
- [ ] Size / file-count limits reject oversized repos with clear errors
- [ ] Path traversal attempts in uploaded ZIPs are rejected
- [ ] Frontend does not store long-lived credentials

---

## 5. Incident Response (Demo Context)

1. If a sandbox appears to hang → kill by container ID and mark job failed.
2. If LLM provider is down → surface clear “provider unavailable” and allow retry.
3. If ledger hash chain is broken → refuse further writes and alert (should be impossible under normal operation).
4. Any suspicion of container escape → stop all sandbox activity immediately and investigate host.
